# Техническое задание — утверждено

Статус: утверждено пользователем 29 октября 2026 года. Рекомендации и открытые вопросы сохраняют указанный в документах статус; численные пороги качества и другие невыбранные параметры требуют отдельного решения.

## Назначение и границы
Система помогает человеку оценить выбранный PR или коммит относительно загруженных ТЗ. Пользователь самостоятельно запускает проверку в CLI; после запуска агент автоматически анализирует данные и показывает результат в CLI. На первой стадии система читает код; самостоятельный запуск агентом кода и тестов проверяемого приложения, публикация результатов в GitHub и управление версиями ТЗ отложены.

## Функциональные требования
- FR-001: пользователь добавляет ТЗ в базу и может перезаписать старые данные. При замене пользователь явно выбирает документ; противоречия требований показываются человеку.
- FR-002: принимаются TXT, Markdown, DOCX и PDF с извлекаемым текстом. Распознавание сканов и изображений не требуется. Пропуски и ошибки извлечения отображаются.
- FR-003: пользователь выбирает ТЗ и PR или отдельный коммит, кратко поясняет, что выполнено в изменении, и запускает проверку. Полное описание всех заданий не требуется.
- FR-004: агент выявляет возможные нарушения затронутых требований и сопоставляет выбранное ТЗ с изменениями, показывая, что реализовано. Краткое пояснение пользователя помогает определить контекст, но не заменяет ТЗ и не является доказательством реализации.
- FR-005: доступ к GitHub осуществляется через MCP; анализ ограничен чтением кода.
- FR-006: ТЗ индексируется и используется через RAG.
- FR-007: CLI предоставляет независимые настройки текстовой LLM и embedding-модели; доступ к каждой осуществляется через свой настраиваемый OpenAI-совместимый API. Embedding-модель может быть локальной или внешней.
- FR-008: язык максимально подробного отчёта выбирается пользователем в CLI; он показывает все обнаруженные замечания, включая спорные, доказательства и ограничения. Подозрение отличается от подтверждённого противоречия.
- FR-009: большие изменения анализируются; недоступные файлы пропускаются. При неполной выдаче MCP допускается частичный отчёт с явным указанием ограничений.
- FR-010: сохраняются история проверок и материалы прошлых проверок, в том числе при перезаписи текущего ТЗ.
- FR-011: пользователь может повторно проверить обновлённый PR; предыдущие результаты остаются в истории.
- FR-012: пользователь может оспорить вывод комментарием; агент повторно рассматривает его. Пересмотр использует сохранённые материалы исходной проверки; обновлённые данные проверяются отдельным запуском.
- FR-013: система сообщает о недостаточности данных и не представляет пропущенный материал как проверенный.

## Нефункциональные требования и архитектура
- NFR-001: пользователю показываются область проверки, источники, пропуски, причина частичного результата и ревизии, если известны.
- NFR-002: исходный код и ТЗ анализируются как данные: требования ТЗ учитываются при проверке, но встречающиеся в них команды не изменяют инструкции агента, настройки или права инструментов. Разрешения задаются приложением.
- NFR-003: совместимость API, корректность технического контракта и измеренное качество модели оцениваются отдельно.
- NFR-004: языки программирования не ограничиваются заранее списком; одинаковое качество для всех языков не заявляется.
- NFR-005: CLI-приложение работает локально на MacBook Pro M5 с 16 ГБ памяти; обе модели могут предоставляться через локальные или внешние API. Масштаб, сроки, бюджет и численные пороги пока не заданы.

Предлагаемая архитектура, контракты и компромиссы изложены в сопутствующих документах. Окончательные пороги качества и ряд продуктовых решений остаются открытыми; см. OPEN_QUESTIONS.md. Критерии привязаны к идентификаторам в ACCEPTANCE_CRITERIA.md.

## Тестирование на отдельном репозитории

- TEST-001: в ходе реализации создать отдельный учебный GitHub-репозиторий с небольшим приложением, ТЗ с идентификаторами требований, синтетическими данными и подготовленными изменениями. Агент обращается к нему через GitHub MCP с правами чтения. Создание и подготовка репозитория выполняются отдельно от работы агента; сейчас репозиторий не создан.
- TEST-002: подготовить ветки, PR, обычные и merge-коммиты для проверки поиска нарушений и реализации требований выбранного ТЗ. Merge-коммит сравнивается с первым родителем; отчёт и эталон указывают SHA родителя. Первый родитель не обязательно основная ветка.
- TEST-003: для каждого сценария фиксировать идентификатор, краткое пояснение пользователя, выбранное ТЗ, репозиторий, PR или SHA коммита, базовую и проверяемую ревизии, применимые требования, ожидаемые реализованные элементы, нарушения, доказательства, контрдоказательства и допустимые ограничения. При неоднозначности допускаются несколько обоснованных выводов или недостаточность данных.
- TEST-004: хранить эталонные ответы в локальном оценочном наборе вне всех областей, доступных анализатору через MCP, RAG и другие средства; во время анализа агент не получает разметку. Имена и описания сценариев не должны раскрывать ожидаемый вердикт.
- TEST-005: набор охватывает реализацию требования, нарушение и его отсутствие, неизменённый код, межфайловое нарушение, разные термины в ТЗ и коде, исключение в другом разделе, поэтапную реализацию, неоднозначное и противоречащее ТЗ пояснение, merge-коммит, недостаточный контекст, повтор и оспаривание.
- TEST-006: штатное чтение PR, коммитов и файлов проверять через работающий GitHub MCP. Недоступность базовой ревизии, timeout, отсутствие patch, усечение и ограничения источника дополнительно проверять управляемыми ответами на границе адаптера. Результаты живого MCP и имитируемых отказов фиксируются отдельно; имитация не подтверждает фактическое поведение GitHub.
- TEST-007: перед сравнением с эталоном проверять ожидаемые ревизии и происхождение полученных материалов. Несовпадение тестового входа и изменение PR во время чтения учитывать отдельно от ошибки модели; при изменении фикстуры актуализировать эталон.
- TEST-008: сохранять протокол прогона: сценарий, входы, профили моделей, настройки индекса, найденные требования, доказательства, ограничения, отчёт и сравнение с эталоном. При изменении моделей, retrieval, обработки документов или алгоритма анализа повторять соответствующие регрессионные проверки.
- TEST-009: оценивать пропуски применимых требований и нарушений, необоснованные обвинения, определение реализации, доказательства и неопределённость. Происхождение цитаты, точность и поддержку вывода проверять раздельно. Численные пороги устанавливаются отдельно после первых прогонов.
- TEST-010: результаты действительны для проверенных сценариев и не гарантируют качество на всех языках, форматах, моделях и размерах проектов. Агент не запускает код проверяемого приложения.

Для выбранного merge-коммита анализ выполняется относительно первого родителя. При недоступной исходной ревизии допускается частичный отчёт о текущем коде с явным ограничением: нельзя утверждать, что обнаруженная проблема внесена выбранным изменением или что реализация добавлена им без сравнительных доказательств.

Пользователь вручную оценивает результаты проверок агента. Исходные варианты embeddings и GitHub MCP выбраны: Qwen3-Embedding-0.6B через Ollama и официальный локальный GitHub MCP; их работоспособность и качество подлежат проверке. Для текущего учебного проекта дополнительные требования к политике хранения и ограничениям внешних API не заданы.
